# 系統架構：IT 事件助理

> 版本：v0.1（待組員確認後可能調整）
> 最後更新：2026-08-31

---

## 概覽

**定位**：協助 IT 維運事件處理的智慧助理。
**技術核心**：LangGraph + RAG + MCP，以本地部署為主。

系統由一個共用基礎層，以及四個功能模組組成：智慧洞察、人員調度、總結追蹤、知識沉澱。四個模組彼此獨立運作，共用同一套 Agent 框架、檢索與工具整合基礎設施。

```
┌───────────────────────── 共用基礎層 ─────────────────────────┐
│      LangGraph Agent 框架  │  RAG 檢索  │  MCP 工具整合       │
│                      本地部署（推論後端）                     │
└──────────────────────────────┬──────────────────────────────┘
                               ↓
┌──────────┬──────────────┬──────────────┬─────────────────────┐
│ 智慧洞察  │  人員調度     │  總結追蹤     │  知識沉澱            │
│ log/SOP  │  行事曆/排班   │  事件報告生成  │  回寫知識庫          │
│ 比對      │  API 整合     │              │                     │
└──────────┴──────────────┴──────────────┴─────────────────────┘
```

## 驗證策略

我們沒有企業授權去拿真實內部 IT 維運資料，因此驗證策略分兩層：

1. **團隊自身的開發協作歷程**作為主要真實資料來源與 demo 場景——GitHub Issues、PR 討論、CI log、真實踩過的 bug 案例。系統從第一天就在處理團隊自己的資料。
2. **公開學術資料集**驗證核心模型能力（異常偵測、分類），確保技術方法本身站得住腳，不只是靠自家小資料集自吹自擂。

| 功能 | 資料依賴度 | 主資料來源 | 補強資料來源 |
|------|-----------|-----------|-------------|
| 智慧洞察 | 高 | 團隊自身 GitHub Issues、PR 討論、CI log | LogHub（github.com/logpai/loghub，HDFS/BGL/Thunderbird/Zookeeper 系統 log，有異常標籤，學界標準 benchmark） |
| 人員調度 | 低 | 團隊自身行事曆/排班 | 不需要外部資料集，屬通用 API 整合能力 |
| 總結追蹤 | 中 | 團隊真實踩過的 bug/issue 討論串 | Kaggle `suraj520/customer-support-ticket-dataset`（只借欄位 schema：type/subject/description/resolution/priority，不用其消費性支援內容） |
| 知識沉澱 | 低 | GitHub Issues 本身、知識庫 | HuggingFace `Noise144/ticket_classification_IT_EN`（18 類 IT ticket 分類，GPT 合成但分類體系可用來校準知識庫標籤設計） |

> 核心邏輯：只有「智慧洞察」真正卡在需要一批已知結論的歷史 case 才能驗證比對準不準，這塊用 LogHub 這種公開、有 ground truth 標籤的 log 資料集做模型能力驗證最扎實；其他三個功能本質上是團隊自己協作資料就是最好的訓練/demo 素材，不需要去生造企業情境。

補充參考：`DavinciTech/BERT_Categorizer`、`TuShar2309/ticket-classifier` 這類 HuggingFace 模型雖然訓練資料沒公開，但它們用的 ITIL 標準分類欄位（Impact/Urgency/Type，12 類服務台分類）值得直接借用當知識庫的分類骨架。

## 各模組說明

### 共用基礎層（`src/shared/`）

| 模組 | 說明 |
|------|------|
| LangGraph Agent 框架 | 四個功能模組共用的 Agent 執行框架 |
| RAG 檢索 | 向量檢索基礎設施，供各模組查詢相關知識 |
| MCP 工具整合 | Agent 呼叫外部工具（GitHub、Calendar 等）的統一介面 |
| 本地部署 | 推論後端，本地優先，外部 API 用量另外標注 |

### 智慧洞察（`src/insight/`）

比對事件 log 與 SOP，找出異常與對應處理方式。

| 功能 | 說明 |
|------|------|
| log 解析 | 讀取 GitHub Issues/PR/CI log，抽取事件特徵 |
| 異常偵測 | 對照歷史 case 判斷是否為已知異常模式 |
| SOP 比對 | 將事件對應到既有處理流程 |

### 人員調度（`src/dispatch/`）

行事曆與排班整合，屬通用 API 整合能力，不特別需要外部資料集。

| 功能 | 說明 |
|------|------|
| 行事曆整合 | 串接 Google Calendar 等既有 API |
| 排班建議 | 根據事件類型與可用人力建議負責人 |

### 總結追蹤（`src/tracking/`）

將事件討論串整理成結構化報告。

| 功能 | 說明 |
|------|------|
| 報告生成 | 從 bug/issue 討論串生成事件報告 |
| 追蹤狀態 | 追蹤事件處理進度 |

### 知識沉澱（`src/knowledge/`）

事件處理完成後回寫知識庫，供未來事件比對使用。

| 功能 | 說明 |
|------|------|
| 知識回寫 | 將處理過的事件整理進知識庫 |
| 標籤校準 | 對照公開 IT ticket 分類 schema，校準知識庫標籤體系 |
